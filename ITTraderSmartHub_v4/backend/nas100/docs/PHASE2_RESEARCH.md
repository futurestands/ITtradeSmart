# NAS100 Phase 2 — Read-only data export and conservative research loop

**State: implemented and locally unit-tested; UNVALIDATED ON REAL NAS100 DATA.**

This adds a research-only workflow **without** changing Flask, Android, Supabase,
`risk_engine.py`, `app.py`, EA source, or broker account permissions.

## Files added

- `backend/tools/export_mt5_nas100.py`: request **closed** MT5 bars from the
  already connected **read-only investor terminal** and write CSV + symbol
  specification snapshot (no account number or password). A Windows MT5
  session is required *for collecting this broker's data*, not for offline
  research or a future phone-only consumer of published analysis.
- `backend/nas100/backtest.py`: conservative synthetic execution proxy for
  signals already generated by the rule engine. Uses next-bar limit fills,
  documented cost floors, stop-first ambiguous candles, and no optimistic
  settlement of unfinished positions.
- `backend/nas100/research.py`: inspect historical bars using **prefixes only**;
  higher-timeframe bars cannot contain future candles. Evaluations do not cross
  a caller-specified dataset cutoff.
- `backend/tools/run_nas100_research.py`: local offline CLI, reads broker CSV;
  prints JSON with explicit assumptions and **null** statistics when no
  completed trades exist.
- Three targeted test modules. No broker requests made during unit tests.

## 1. Establish a protected investor-only MT5 terminal session

On your development **Windows PC**, the operator must establish the intended
investor-only **demo** account. Both terminal and account trading flags, including
expert permission, must be disabled. These flags do not prove password provenance.
The CLI checks that the exact terminal path is already running before attachment;
it never logs in, switches accounts or changes permissions. Never put account
credentials in these commands or share them in screenshots.

## 2. Collect actual NAS100-related historical bars

From `ITTraderSmartHub_v4/backend`:

```powershell
$py = '.\.venv-gateway\Scripts\python.exe'
& $py tools\export_mt5_nas100.py --symbol USTECH100M --timeframe M5 --count 10000 --out-dir data\nas100
```

Expect `data/nas100/USTECH100M_M5.csv` and the associated
`.metadata.json`. Account number, passwords and tokens are deliberately
excluded. Review licensing before uploading broker data anywhere.

Some brokers provide limited history. The reported bar count may be below
10,000. UTC timestamps are used throughout. The exporter excludes position
zero (normally still forming) and any candle not closed at collection time.
An actually future-dated bar open aborts the whole capture rather than silently
repairing the broker clock. Excluded current/unclosed bars are counted. Account
identity and permissions are rechecked before/after history and before publication.
Existing captures are never replaced; choose a new output directory for each run.
CSV hashes, current specifications and unclassified gaps are recorded. Every fresh
capture remains `TIMEBASE_UNVERIFIED` and `research_eligible=false` initially.

## 3. Inspect real broker specifications and costs

The metadata contains a **current** symbol-specification snapshot. Use its
`point` value for `--point-size`. Historical spreads are saved in the CSV;
choose an explicit stress floor for `--spread-points`. Known entry/exit bar
spreads can widen this floor; the greater of the floor and observed entry/exit
spreads is deducted once, plus slippage on each side and round-trip commission.
Brokerage
commission and slippage assumptions also need evidence. Do not invent values
and publish the resulting backtest as a performance claim.

## 4. Run the slower, transparent historical analysis

```powershell
& $py tools\run_nas100_research.py --csv data\nas100\USTECH100M_M5.csv `
    --point-size <BROKER_POINT_SIZE> --spread-points <CONSERVATIVE_SPREAD_POINTS> `
    --slippage-points-per-side <DOCUMENTED_SLIPPAGE> `
    --commission-points-round-trip <DOCUMENTED_COMMISSION> `
    --timebase-evidence <OPERATOR_VERIFIED_TIMEBASE_JSON> `
    --metadata data\nas100\USTECH100M_M5.metadata.json `
    --base-minutes 5 --htf-minutes 60 --start 1000 --stop 1500 --stride 5
```

Replace placeholders with documented broker/scenario values. Missing slippage or
commission assumptions are not silently treated as zero in real-data research.
The metadata must match CSV hash, symbol, timeframe, row count and point size.
The existing `bot.time_integrity` gate verifies closed/future bars, clock
uncertainty, timeframe grid and explicit allowed session gaps from local operator
evidence. A manual document is an operator assertion, not broker attestation.
Without these inputs the CLI returns `BLOCKED_DATASET_ELIGIBILITY` with null
counts/statistics. It never presents an unrun study as a zero-signal result.

The evidence JSON uses `TimebaseEvidence` fields: `status='VERIFIED_UTC'`,
`source`, `observed_at_utc`, `timeframe`, `grid_origin_epoch_seconds`,
`clock_uncertainty_seconds`, and optional `allowed_gaps` listing exact UTC
missing-span boundaries. Do not set VERIFIED_UTC without independent evidence.
The engine still conservatively blocks recent gaps rather than guessing closures.

For deliberately generated synthetic smoke fixtures only, `--synthetic-fixture`
bypasses real-data provenance gates and labels the output
`SYNTHETIC_FIXTURE_UNATTESTED`, with `performance_validated=false` and
`model_trained=false`. This flag does not approve an actual broker dataset.

The `--start`, `--stop` and `--stride` values limit scans because the reference
implementation is intentionally not optimized for multi-year datasets.

If no signals, `signals=0` and `expectancy_r=null` is a correct result — not a
coding failure by itself. We must not lower filters merely to force a positive
outcome.

`decision_counts` reports every inspected BUY/SELL/NO TRADE decision separately
from deduplicated setup observations (`signals`) and single-position proxy
outcomes (`summary.signals`). All reported outcome values are additive R units,
not money, portfolio returns, independent performance validation or probabilities.

## 5. What the simulator cannot prove

- It does not know the intrabar sequence from OHLC; when both stop and target
  are touched, it books the stop first.
- On an intrabar limit entry it does not credit a possibly earlier target touch;
  an entry at the open or a close proving a later target crossing is required.
- It approximates a single reference OHLC price and subtracts explicit costs
  in instrument price points. It is **not a tick-replay execution simulator**,
  nor a broker-verified P&L/lot-sizing engine.
- It does not model orders rejected for margin, tick size, stop distances,
  market gaps at entry, order queue, partial fills, news-event halts, rollovers,
  holidays or broker slippage distributions.
- It does not train machine learning or produce calibrated probabilities.
- The unit tests only exercise synthetic examples. Only multi-regime real
  historical data and held-out testing can begin to establish an edge.
- Running the exporter on a developer's Windows host **does not solve**
  automatic multi-user phone-only broker account synchronization. That still
  needs authorized broker APIs or managed isolated MT5 infrastructure.

## Security and review controls

No trade execution was added. Keep a read-only investor session, protect CSVs,
and never expose the Flask dev server to the public internet. The isolated
package should be reviewed and merged into the user's **latest** project,
which may be newer than public GitHub commit `161edd2` and reportedly includes
Supabase. Do not overwrite that local work or deploy an unvalidated model.
